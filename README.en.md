# NodeX

A node-side daemon. It applies panel-issued configuration and user lists to Xray and Hysteria 2 kernels, then reports traffic and liveness back to the panel.

[中文](README.md) · [Router build](https://github.com/wooxi/nodex-luci) · [Container build](https://github.com/wooxi/nodex-docker) · [Control panel](https://github.com/wooxi/xpanel)

---

## What it is

NodeX runs on the node server, between the panel and the kernel. It ships no sign-up, subscription or billing UI — that belongs to the panel. NodeX does four things: pull configuration, push user lists, collect traffic, supervise kernel processes.

A single instance hosts multiple nodes. Each node is its own kernel process with its own listening port, its own sync loop and its own state.

**This repository is the single source of truth for NodeX.** The router and container builds are distribution channels; they do not carry a copy of the source and pull it at build time.

## Builds

One Go codebase, three ways to install. The UI layer differs; the capability does not.

| Build | Repository | Artifact | Target |
|---|---|---|---|
| Standard | this repo | single binary | Any Linux (Debian / Alpine / systemd) |
| Router | [nodex-luci](https://github.com/wooxi/nodex-luci) | `nodex_*.ipk`, `luci-app-nodex_*.ipk` | OpenWrt x86_64, integrated into the LuCI menu |
| Container | [nodex-docker](https://github.com/wooxi/nodex-docker) | `ghcr.io/wooxi/nodex-docker` | Docker / Synology / VPS, mountable data dir |

Standard and container builds ship a built-in Vue 3 admin UI on `:8888`. The router build plugs into LuCI and is reached through its reverse proxy, so it occupies no extra port.

## Capabilities

**Protocols**

| Protocol | Transport and security |
|---|---|
| VLESS | Reality / TLS / WebSocket; Reality supports `dest`, `serverNames`, `shortIds` |
| VMess | TCP / WebSocket / TLS |
| Trojan | TLS / WebSocket |
| Shadowsocks | `2022-blake3-*` AEAD suites |
| Hysteria 2 | QUIC, Salamander obfuscation, declared up/down bandwidth |

**Node management**

- Multiple nodes per instance, each with a dedicated kernel process, port and sync cycle
- Automatic restart after abnormal kernel exit; exit code and restart count exposed in the UI
- Kernels can be downloaded, swapped and upgraded independently; artifacts persist in the data directory and survive container recreation
- Per-node enable and disable

**Panel integration**

- User sync: the panel's active users become the kernel-side allow list, including expiry and quota checks
- Node parameters: port, bandwidth, obfuscation and certificates follow the panel; local config is a fallback only
- Traffic reporting: up/down deltas aggregated per user
- Liveness: online IPs and node heartbeat
- If the panel is unreachable, the current configuration keeps serving and resumes reporting once the panel returns

**Forwarding mode**

For deployments where ingress and egress are separate hosts: panel inbound traffic is forwarded to landing servers.

- Weighted load across multiple targets
- WebSocket keepalive with configurable interval
- The forwarding path is independent of the node protocol and does not change the node type on the panel

## Installation

### Standard build

Download the binary for your architecture from [Releases](https://github.com/wooxi/nodex/releases):

```bash
install -m 755 nodex-linux-amd64 /usr/local/bin/nodex
nodex -version
```

Two kernels are required at runtime: `xray` and `hysteria`. NodeX loads them from `/usr/bin/xray` and `/usr/bin/hysteria` by default; both paths are editable in the UI.

```bash
nodex start                    # runs in the foreground, supervised by your init system
nodex stop
nodex restart
nodex -config /path/to/config.json
```

Open `http://<host>:8888` on first start to set the admin password. The configuration file lives at `/etc/nodex/config.json` and is generated by the UI — there is nothing to edit by hand.

### Router and container builds

See [nodex-luci](https://github.com/wooxi/nodex-luci) and [nodex-docker](https://github.com/wooxi/nodex-docker). The UIs differ; the panel steps are identical: enter the panel URL and communication key, then assign each node its panel node ID and protocol.

## Boundary with the panel

NodeX and the panel share an HTTP contract and nothing else — no shared code, no shared database, no runtime dependency.

| | Panel | NodeX |
|---|---|---|
| User data | authoritative | read-only cache, refreshed periodically |
| Node parameters | authoritative | read-only cache, local fallback when the panel is unreachable |
| Accounting | persists and settles | collects and reports |
| Subscription generation | responsible | not involved |
| Kernel processes | unaware | starts and reaps them |

Any panel implementing UniProxy can drive NodeX, and NodeX can be replaced by any node daemon implementing the same contract.

## Requirements

| Item | Requirement |
|---|---|
| OS | Linux x86_64 / arm64, statically linked, no glibc dependency |
| Go | 1.26 (build only) |
| Kernels | Xray-core, Hysteria 2 |
| Panel | Xboard, V2Board, or any UniProxy-compatible implementation |

## Building

```bash
cd webui && npm ci && npm run build && cd ..
CGO_ENABLED=0 go build -ldflags "-s -w -X main.version=$(git describe --tags --always)" -o nodex ./cmd/nodex
```

The frontend is embedded with `go:embed`, so the result is a single static executable.
